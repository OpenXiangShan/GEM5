# PerfCCT 采集与字段检查

按当前问题选择检查项，不要求重新编译或全量扫描数据库。

## 复用数据和采集验证

SQLite 可用 `sqlite3.connect("file:/path/to/trace.db?mode=ro", uri=True)` 只读打开。先查 `sqlite_master` 的实际表名，再用 `PRAGMA table_info(实际表名)` 检查字段。大表查询先限制列和窗口，必要时检查查询计划；需要索引时优先在分析副本操作。

某些历史 `LifeTimeCommitTrace` 数据需要用 `AtCommit > 0` 排除未提交行；先查当前写入逻辑，不能把它当作通用过滤器。确认 warmup/ROI/退出时的统计边界，CSV 和数据库未必跟随 stats reset；只有验证过前缀一致性后才做差分。

采集前查当前代码中的写入点、配置入口及工具帮助。编译宏、表定义和 dump 开关存在，不代表生成的写入函数不是空桩。短运行验证表非空、关键字段有效、成功退出，以及主 stats 是否与预期一致；不要直接复用改变微结构配置的旧 debug 命令。

限制 trace 输出时保留热身过程和必要的生产者/事件上下文，不要把缩短采集窗口等同于缩短实际预热。

## 最小字段语义表

| 字段类别 | 需要核对的区别 |
| --- | --- |
| Fetch/Dispatch | valid、fire、接受、重试；首次还是最后一次时间 |
| Ready/Issue | 操作数就绪、仲裁选中、发射接受、取消 |
| Execute | FU 完成、bypass 可用、writeback，是否同一事件 |
| Commit | 真实提交、占位零值、squash 行是否保留 |
| ID | 指令实例、预测块还是队列槽位；是否复用及如何区分代次 |

缺失 ready/资源分配字段时，不凭阶段名把等待拆成精确的资源占用或仲裁代价。RTL 首次 valid 时间与 GEM5 被重试覆盖后的时间，也不能直接比较为相同阶段。

## 历史案例中的归因限制

Astar 调查曾以“下一条已提交指令 Fetch 晚于分支结果可用”筛恢复候选，总量与退休误预测一致，但这仍不是显式 redirect 的逐事件证明。

共同样本中首条正确路径 FU 延迟中位数均为 16 cycles、均值差约 0.217 cycles，只削弱统一恢复惩罚差异的解释。扩大到后续 32/64 条指令时，窗口差异可能混入再次恢复、访存和有效执行。筛掉再次恢复会改变样本构成，不能把均值下降直接认定为它的周期贡献。
