# PerfCCT 时序分析

目标是把时序疑问转成可验证的局部事件证据。可只分析一边，也可跨模型对拍；不要求所有性能问题都使用 PerfCCT。

## 何时值得使用

先考虑：要区分什么时序假设？trace 是否暴露必要事件？答案是否会改变下一项实验或模型选择？

| 问题 | 可检查的时序证据（以实际字段为准） |
| --- | --- |
| 恢复是否更慢？ | 分支结果/redirect 到正确路径 Fetch、执行、Commit |
| 指令为何晚执行？ | Dispatch、就绪、仲裁/发射、执行以及生产者完成时间 |
| 前端少供给还是后端推进慢？ | 同一动态指令或窗口的阶段间隔及供给空洞 |
| 长尾来自哪里？ | 慢样本上下文中的 miss、replay、再次恢复、依赖链 |
| 两边哪里开始分歧？ | 匹配实例的局部阶段差、窗口内差异首次出现或扩大 |

字段不足时只能定位疑点，不能确定原因。TAGE provider、SC gate、训练表项等问题需要模块专项 trace。只有总分差、尚未缩小范围时可优先看 stats 或 A/B；已有 trace 也可用于低成本探索。

## 先确认 trace 实际记录了什么

查写入点和 schema：阶段与单位、valid 还是 fire/接受、首次记录还是最后覆盖、零值含义，以及 squash/replay/未提交指令是否留表。表名含 Commit 不保证每行已提交。

只建立必要字段对应，分开可比阶段与仅单边可见阶段；到达时间不等于资源分配、占用或回收时间。

## 建立动态实例关联

单边使用可靠的本地实例 ID；跨模型优先通过共同提交指令/控制流建立对应，再映射回各自预测或训练事件。用 PC、实际方向、nextPC 和上下文验证，消除循环中重复实例的歧义。

- 本地序号、周期不能跨模型直接互等；第 k 条记录可能受错路、重试或训练次序影响。
- 不以预测相同作为配对条件，否则会排除要调查的分歧。
- 报告未匹配项、覆盖率、跳过区间和重同步情况；丢弃跨重同步点、尚未完成的分析窗口。
- 提交轨迹只展示存活路径，不能还原全部错路执行或 squash 原因。

## 围绕事件分析时间

各自以同一逻辑事件为时间原点。先统一时间单位，不能直接相减两边绝对 ticks。

依假设选择配对样本、长尾或短窗口，报告样本数，不预设固定窗口长度。长窗口可能包含有用执行、miss、再次恢复；筛选子集会改变样本构成，不能把筛选前后的均值差直接当作周期贡献。依赖等待与资源阻塞可能重叠，也不能直接相加。

用同一 ROI 的退休数、事件数和运行成功状态校验结果。候选事件总数吻合，不等于已完成显式 redirect 的逐事件关联。

## 采集与结论的边界

优先复用已有数据库。新采集先确认写入函数不是空桩，用短运行验证表非空、字段可用和时间戳语义；限制输出范围时保留预热状态。若观测版改变主性能统计，先解释变化再用于归因。

结果应说明问题、数据来源与窗口、事件定义、关联覆盖率、关键证据、替代解释和下一项验证。排除一种解释也有价值，不必每轮都产生代码修改。

实际操作时按需阅读 [采集与字段检查](references/trace-checks.md)；选择整体调查方向时参考 [rtl-performance-alignment](../rtl-performance-alignment/SKILL.md)。
