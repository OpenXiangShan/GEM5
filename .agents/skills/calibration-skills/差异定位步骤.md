**前置准备：先克隆 GEM5 和 XiangShan 源码仓库。** 在工作区根目录执行：

```bash
git clone git@github.com:OpenXiangShan/GEM5.git
git clone git@github.com:OpenXiangShan/XiangShan.git
```

本工作区根目录为 `/nfs/home/zhenhao/AUTO-Calibration`。若对应目录已有上述仓库，直接复用，并核对 `git remote -v` 中的来源，无需重复克隆。后续从确认的实验基线新建分支，再修改、编译和验证。

**输入：** 一份已经指出 XS-GEM5 与 XS-RTL 哪个子项或切片误差大的 Markdown 报告。**输出：** 优先查哪个 feature、它的哪条行为规则不同、证据能解释多大范围的性能差距。这里不重做周回归评分或 INT/FP 排名。

排查顺序：**把 AM 拷贝到自己的工作目录并配置路径 → 复用报告里的原始数据 → 用计数器筛出两三个候选 → 用同一 ROI 的开关或补丁对照排序 → 给头号候选抓局部 trace、读两端源码 → 用 atoms benchmark 单独验证待对齐的规则。** 如果已有个人 AM 副本、对照或 trace，直接复用；缺哪一环才补哪一环。

## 1. 准备自己的工作目录，拷贝并配置 AM

先把 `/nfs/home/share/zhenhao/nexus-am-xs` **整个目录**拷贝到自己的路径下，保留 `am/`、`libs/`、`cliff/` 和构建文件。后续复用自己副本中的基础设施，新增测试、修改 Python 生成器、编译镜像都在副本中进行。不要只拷贝 `cliff` 或单个 `benchmarks.py`，它们还依赖 AM 运行时、库和公共生成工具。

以下命令中的 `/path/to/your/diff-work` 替换为自己的可写绝对路径；`AM_HOME` 指向完整的 `nexus-am-xs` 根目录，不是其中的 `am/` 子目录：

```bash
export DIFF_WORKDIR="/path/to/your/diff-work"
export AM_HOME="$DIFF_WORKDIR/nexus-am-xs"
mkdir -p "$DIFF_WORKDIR"

# 首次使用才拷贝；后续复用已有副本，保留自己的修改。

fi

mkdir -p "$DIFF_WORKDIR/results"
```

若已有个人 AM 副本，可直接把 `AM_HOME` 设为该副本的绝对路径，跳过拷贝；确认它不是指回原目录的软链接。新终端需重新设置 `DIFF_WORKDIR` 和 `AM_HOME`。运行前核对脚本及 Makefile 中的路径，确保使用自己的 `AM_HOME`；如果脚本写死了原 AM 路径，在副本中改为自己的路径。

记录 AM 来源、版本和本地修改。生成的 C 文件、头文件和镜像保存在个人 AM 的测试目录中；新实验的命令、日志、计数器和 trace 放在 `$DIFF_WORKDIR/results/<实验名>/` 下，供后续对照复用。文中指向原 `nexus-am-xs` 的链接用于查阅示例，实际操作使用 `$AM_HOME` 下的对应文件。

**源码分支约定：有对齐实现时，先新开分支尝试。** 涉及 GEM5 或 XiangShan 的实现修改、隔离补丁或插桩时，在要修改的仓库中从本次实验确认的基线执行 `git switch -c align/<feature>-<日期> <基线提交>`，再修改、编译和验证；新的独立尝试使用新的分支名。记录分支名、基线提交和实验提交，保持主线分支用于更新。复现历史报告时，从报告对应基线建分支；验证当前主线时，从更新后的主线提交建分支。

**GEM5 直接使用原仓库目录。** 在 `GEM5` 中检查工作区状态，然后从确认的基线新建实验分支，并在此目录修改、编译和验证。默认不另建 GEM5 worktree，不把实现放到 `/tmp` 或另一个克隆中；个人 AM 副本和实验日志、trace 仍放在 `$DIFF_WORKDIR`。已有临时工作树中的实现应先保存提交，再在原目录新建分支并应用这些提交，核对与已验证版本的代码一致性。交付时让原目录停留在本次实验分支，记录原分支、本次基线、最终提交和日志路径；保留已有分支、日志及用户修改。若未提交的用户修改妨碍切换，先保护这些修改，不覆盖或丢弃。

**每次 `git pull` 更新 GEM5，都先切回 `xs-dev`。** 确认实验修改已保存在原实验分支、工作区可安全切换后，在 GEM5 仓库中执行 `git switch xs-dev && git pull --ff-only origin xs-dev`；其中 `origin` 应对应 OpenXiangShan/GEM5，远端名不同时替换为实际名称。已有对齐分支继续保留，不在该分支上直接拉取主线，也不把未提交的实验修改带入 `xs-dev`。按[差异查找步骤第六步](./差异查找步骤.md)汇报更新前后提交及冲突情况；本地修改阻止安全切换、主线无法快进或出现冲突时，暂停该仓库的相关操作并询问人工处理。实验分支与主线分叉本身不妨碍切回 `xs-dev` 更新，主线更新也不改变已固定的实验基线。

## 2. 从报告摘出一个能复现的差距

**用户指定的输入优先。** 指定了目录、运行编号、checkpoint、配置或正式测量段（ROI），就按指定值分析；只从报告和对应的回归网页补全未指定的项。指定路径不可读，或两端的 checkpoint、配置、ROI 对不上时，说明具体缺哪一项或哪里不匹配，不要自行换用其他运行。

**未指定路径时，复用对应回归网页公布的大机房归档路径。** 按[差异查找步骤：从评分追到原始数据](./差异查找步骤.md#从评分追到原始数据)找到两端的归档。以 `mcf_12886` 为例（gem5 #123、RTL #22；换运行时要从该次网页重新取路径）：

- **gem5：** 在 `align_test_spec06` 对应配置的 Summary 中读 `Archive output` → `Path`。本例的切片计数器文件是 `/nfs/home/share/gem5_ci/performance_data/spec06-rva23-novec-gcc16-1.0c/20261113_060646_f9649a04ee_kmhv3_run123/spec_all/mcf_12886/m5out/stats.txt`。
- **RTL：** 在同配置的评分文件中读 `Other Information` → `Data Directory`。本例从 `/nfs/home/cirunner/perf-report/cr261113-8b15f0652-DefaultConfig/mcf_12886_0.149435/simulator_err.txt` 取 `[PERF]` 计数器，用同目录的 `simulator_out.txt` 核对实际加载的 checkpoint。

记下子项、checkpoint、双端版本及补丁、配置、ROI 和两端原值。若报告只给了分数，从上述文件取数；核对提交指令数、预热重置点和时钟后，再算 `ΔCPI = gem5 CPI − RTL CPI`。已给出切片和窗口时直接用，不再重选。

若只给了子项，按 `切片权重 × ΔCPI` 看谁贡献了主要差距，保留正负号，再选一个误差小的对照片。例如 #123 基线中，`mcf_12886` 占 `mcf` 加权 CPI 净差的 **23.92%**；`mcf_11326` 权重相近但只占 **3.94%**。先查 `12886`，不必一开始就给 18 个切片全部打开 trace。[切片选择与原值](./mcf-性能差异分析.md)

## 3. 把计数器异常改写成能检验的假设

从同一 ROI 取数：事件数换算为每千条退休指令，比率保留分子、分母，延迟注明起止事件。**事件同名但统计边界不同，只作线索，不算“多花了多少拍”。** 每个候选都要回答：“如果真是它，哪个中间事件会跟着变？”

| 报告里看到的现象 | 优先拆分的 feature | 最省事的区分方法 |
|---|---|---|
| 前端停顿多 | 分支预测、误判恢复、L1I 取指 | 分开看提交分支误判 MPKI、误判恢复拍数、需求取指 miss MPKI；不要把取指等待全算给预测器 |
| load 翻译慢、PTW 流量大 | DTLB 首发 miss、L2 TLB、页表遍历或重放 | 看首发 miss、PTW→L2 请求和翻译完成时间；若已有 TLB PR，从同一基线单独应用，检查流量下降时 CPI 是否也靠近 RTL |
| 普通需求 miss 不更多，但预取流量差很多 | 某个预取源的训练资格、步长预测或发送过滤 | 按**来源**分别看训练、候选、实际发出、有用数。训练数先分岔就查输入；训练近似而候选分岔才查预测表；候选近似而发出分岔再查过滤与仲裁 |
| 需求请求数接近，但返回慢或重放多 | L1D bank、MSHR 分配/合并、L2 仲裁、DRAM 排队 | 分开量“请求→准入”“准入→发往下层”“下层接收→返回”。若上游预取流量已不同，先控制流量，不要仅凭 MSHR 占用高就判容量不足 |

`mcf_12886` 提供了一个反例：初筛时 gem5 / RTL 的分支误判为 **0.418 / 0.421 MPKI**，普通 L2 读 miss 率为 **21.78% / 23.93%**，但 gem5 更慢。这降低了“误判更多、普通读漏得更多”的优先级，并没有排除翻译、预取竞争或返回路径。若报告只有分数，没有双端事件，此时只能给候选，不能给根因。[计数器初筛](./mcf-性能差异分析.md)

## 4. 用单因素对照给候选排序——看谁缩小差距，而不是谁变化最大

需要修改源码实现对齐规则或应用隔离补丁时，先按第 1 节约定新建实验分支，再开展以下对照。

固定 RTL、gem5 基线、checkpoint、ROI 和内存配置。每次只切一个来源、替换一条规则或叠加一个隔离补丁；新跑时按各自 CI 构建并核实 DRAMSim3 配置。已有实验能回答问题就不重跑。对同一测量指标计算：

`差距回收率 = (|基线 − RTL| − |干预后 − RTL|) / |基线 − RTL|`。正值表示靠近 RTL，负值表示更远；基线差为零时不算百分比。优先查**回收幅度大、且中间事件按预测变化**的候选。不同切片、窗口、基线的比例不能混排，各干预的收益也不能相加。

**实测示例：** `mcf_12886`，gem5 #123 加两个 TLB 补丁，对照 RTL #22；20M 预热后的同一正式测量段。基线为 gem5 **29,311,048**、RTL **23,635,725** 周期，差 **5,675,323** 周期。[完整对照及原始计数](./mcf-12886-trace/sensitivity/全长对照.md)

| 只改 gem5 的哪一项 | 改后与 RTL 的周期差 | 回收率 | 排查决定 |
|---|---:|---:|---|
| 只关 SStride，保留其他预取源 | +939,255 | **83.45%** | 优先拆解 SStride 的训练、候选、发出三步；不是建议关闭预取 |
| 改 ROB 压缩配置（策略和组上限一起变） | +5,511,406 | 2.89% | 可影响退休的分组，但该组合对总差的解释力小 |
| 延后 DRAM rank 刷新 | +7,091,012 | −24.94% | 可解释个别请求的长尾，不是缩小整段差距的方向 |
| L1 DTLB 从 48 扩到 2048 项 | +11,719,135 | −106.49% | 对容量敏感，但**更慢了**；不能由 TLB miss 多推出“应先扩容” |

近期 PR 也可以这样筛：[mcf 全部 18 个切片的隔离实验](./mcf-TLB-PR验证报告.md)中，#1323 缩小原有加权 CPI 差的 **9.39%**，再叠加 #1310 则无额外变化。这解释了为什么保留 TLB 改进、继续追剩余差距；它与上表的单切片回收率不是同一分母。

## 5. 对头号候选，找第一条不同的硬件事件

先用退休 trace 或 PerfCCT 找到累计周期差最大的**动态窗口**；再按同一架构指令序列、PC 和 VA 配对，在该窗口打开详细事件或 RTL 波形。不要用两端绝对时间戳或各自的 ROB 编号硬配，也不要把退休最晚的指令直接当作根因。

本例窗口是 `0x108d2: lw t4,24(a5)` 退休到下一次同 PC 退休。深入 SStride 时，只问一串有先后关系的问题：**首发翻译是否命中 → 是否重放 → 是否允许训练 → 有没有生成候选 → 有没有真正发出？** 历史基线的四次连续访问中，旧 gem5 都训练了，第四次生成两个候选；RTL 四次都是首发 TLB miss，都没进步长表。读两端对应版本源码：RTL 的 `NewLoadUnit.scala` 要求 `tlbHit && isFirstIssue` 才给有效训练事件，`PrefetcherWrapper.scala` 再筛 miss 或 SStride 来源命中；旧 gem5 的 `sms.cc` 看到了重放后的 L1D miss，却未检查首发资格。**到这里，结论才从“预取流量不对”落到“SStride 对首发 TLB miss 的 load 是否在重放时补训”。** [同笔 load 的事件表](./mcf-12886-trace/stride-audit/same-load-events.csv) · [源码和波形对照](./mcf_12886-SStride与缓存对齐.md)

## 6. 生成 atoms benchmark，在 gem5 和 RTL 上验证 feature 假设

**先看假设是否依赖地址翻译，再选测试环境。** 对步长、缓存行、MSHR 等只需控制物理访存模式的实验，优先复用第 1 步个人副本中 `$AM_HOME/cliff` 的现有用例和标准 AM 构建（[目录参考](./nexus-am-xs/cliff/)）。当前 `cliff` 步长示例直接访问物理地址，不提供虚拟页表控制；只改地址常数或让地址跨过 4 KiB 边界，不能据此构造首发 DTLB miss。若假设涉及 TLB、PTW 或虚拟别名，须另选能建立并启用页表的环境，或先在个人副本中扩展并验证 `cliff` 的运行时支持。

1. **写出待测规则和预期。** 例如，要验证 SStride 的首发翻译门控，两组都启用相同的 Sv39 页表，固定目标 load 和物理数据，使两组目标访问都发生 L1D miss。只改变预热的虚拟页：对照组预期首发 DTLB hit，旧 gem5 和 RTL 都训练；触发组预期首发 DTLB miss，重放后旧 gem5 补训、RTL 不补训。用 trace 核实两组的首发翻译结果。
2. **在个人 AM 副本中写 Python，生成并编译用例。** 可参考 `$AM_HOME/cliff/prefetch/stride_threshold_test/benchmarks.py`（[源码参考](./nexus-am-xs/cliff/prefetch/stride_threshold_test/benchmarks.py)），在 `$AM_HOME/cliff/<类别>/<测试名>/` 下新建测试目录，编写自己的 `benchmarks.py` 并配套 Makefile，生成触发组和对照组。保留示例与 `cliff/utils` 的相对目录关系，固定循环体、步长、访问次数及 ROI，只改变待测条件。进入自己的测试目录后，用 `python3 benchmarks.py` 生成 C 文件和头文件，再参考副本中的 `make_bin.sh`（[脚本参考](./nexus-am-xs/cliff/prefetch/stride_threshold_test/make_bin.sh)），按 `ARCH=riscv64-xs` 和自己的参数编译；Makefile 通过 `$(AM_HOME)/Makefile.app` 复用个人副本的构建基础设施，不必照搬示例的全部组合。
3. **两端运行个人副本生成的同一份二进制。** 每组只编译一次，将自己测试目录生成的同一镜像分别交给 gem5 和 RTL；按第 2 节记录的配置运行，保持 DRAMSim3 配置、预热方式和 ROI 边界一致。在 `$DIFF_WORKDIR/results/<实验名>/` 下保存生成参数、镜像路径及校验值、两端运行命令、ROI 指令数与周期，以及能看到目标事件的计数器或局部 trace。
4. **按事先写下的预期判定。** 先确认两组都达到了设计条件，再逐组对比两端同一条 load 是否进入 SStride 训练。若只有触发组按预期分岔，结果支持该规则差异；若触发条件成立但事件不符，就修正假设；若条件没触发或事件不可见，则不能下结论。微基准回答的是“这条规则是否不同”，它对原切片贡献了多少周期，仍需回到原 ROI 做单因素对照。

**已跑通的例子（独立 Sv39 裸机，不是标准 `cliff` 用例）：** [SStride atoms benchmark 双端实测](./atoms-sstride/README.md)保留了生成器、同一条 load 的逐次观测、RTL 波形和复现命令。首发 DTLB miss 组中，三次目标访问在旧 gem5 都训练，对齐后的 gem5 与 RTL 都不训练；首发 hit 对照组则三者都训练。

## 7. 交付时把“已定位”与“还没证明”分开

| 最终要回答的问题 | 本例能给的答案 |
|---|---|
| 优先修哪个 feature，依据是什么？ | **L1D SStride 的训练资格**。单独关闭该来源，正式段差距缩小 83.45%；这个数字包含流量改变对 L1D、L2 和 MSHR 的反馈，不是训练条件本身的独立贡献。 |
| 哪条具体规则已验证？ | 同一笔 `sn=1104` 的 `0x108d2`，两份 gem5 trace 都是首发 TLB miss、重放后 L1D miss；旧规则训练，新规则不补训。30,004 条指令前缀里，这类错误训练从 **1,882 次降到 0**；正常首发 miss 仍能训练。[A/B 日志与复核命令](./mcf-12886-trace/sstride-implementation/README.md) |
| 哪些结论还不能写？ | 不能说新规则已回收正式段的 83.45%，也不能给剩余周期指定 MSHR 或 L2 的份额。要回答前者，需用新规则重跑完整 ROI；要区分后者，需固定训练输入后再分别改变下游规则。 |

换一个子项时，沿用同一交付格式：**候选 feature 与规则 → 口径一致的双端原值 → 单因素干预前后与 RTL 的差距 → 首个分岔事件及源码/日志 → atoms benchmark 的预期与双端实测（未运行则注明）→ 尚未验证的范围**。这样即使暂时只有候选，也能明确下一次最值得跑哪一个实验。
