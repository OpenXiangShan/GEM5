# CPU 模型与 RTL 性能对齐

目标是解释性能差异并找到有机制依据的模型改进。以下是决策框架，不是固定步骤；根据负责人目标、现有证据和运行成本调整顺序与深度。已确认的比较条件可以复用。

## 建立可解释的比较

确认影响结论的边界：workload/编译器、checkpoint、模型与 RTL 版本和配置、reference、预热和 ROI。相同切片名不保证相同窗口；采集 trace 的配置也可能改变微结构行为。

按实际退休指令数计算 CPI/MPKI，说明百分比分母。区分单切片、定向抽样与全 workload 加权结果。同名计数器先核对事件、统计阶段和分母；Topdown 分类、执行误预测、退休误预测不能仅凭名字映射。

## 先判断方向是否值得追

把假设写成短因果链：哪个行为不同 → 改变什么等待/竞争/恢复 → 为什么影响程序周期，并说明什么观察会支持或削弱它。

可先用事件差额与假设有效代价估算量级，再决定是否做小型 A/B、资源放宽或受控扰动。恢复窗口长度不等于净周期损失；MPKI 相对差小也不意味着性能影响小。

区分三种结论：

- **观察事实**：某窗口多了多少事件、哪里出现时间差。
- **模型内敏感性**：改变一个因素后，程序周期实际变化多少。
- **根因归因**：真实的不对齐机制确实造成了这些差异。

敏感性大说明值得调查，不证明找到了根因；敏感性小只削弱本次探针覆盖的假设。随机扰动、无限资源、禁用组件等探针不能直接作为硬件修复，多个有反馈的探针效果也不能相加。

## 选择能区分假设的最便宜证据

| 当前问题 | 可优先使用的证据 |
| --- | --- |
| 差距集中在哪些 workload/切片/事件？ | 原始 stats、可比的加权或逐点汇总 |
| 某种差异足以产生明显周期影响吗？ | 量级估计、最小机制 A/B 或敏感性探针 |
| 时间花在等待、执行还是恢复？ | 已有 PerfCCT 生命周期 trace、小窗口时序分析 |
| 为什么预测来源、SC 决策或训练状态不同？ | 模块专项 trace 与源码语义对照 |
| 如何把已确认机制实现成模型？ | 行为级建模、针对性验证 |

优先复用已有结果；新运行先确认输出足以回答问题，再选择代表切片、窗口和并发规模。按主要因素隔离实验，检查有效配置与基线；保留真实控制流和资源反馈，明确探针省略了什么。不要为了缩短采集而无意改变预热状态。

## 从总量走到事件

按差异贡献缩小范围，热点不一定是单边事件数最多的 PC。逐事件对拍前，先确认比较的是同一动态实例与同一阶段语义。两边时间戳、本地 ID、同一 PC 的第 k 条记录通常不能直接互等。

按需使用 [perfcct-analysis](../perfcct-analysis/SKILL.md) 分析生命周期时序；TAGE 语义和预测器 trace 分别参考 [rtl-tage-alignment](../rtl-tage-alignment/SKILL.md)、[tage-trace-workflow](../tage-trace-workflow/SKILL.md)；实现机制时参考 [cpu-performance-modeling](../cpu-performance-modeling/SKILL.md)。无需默认加载全部。

## 收束与下一步

每轮留下足够复查的版本/配置、命令或数据来源、窗口、关键统计和结论边界；简要区分已确认事实、假设与下一项有区分力的实验，不要求固定报告模板。

当影响量级不足、实验持续不支持、关键观测缺失或已经回答当前问题时，降低优先级、补最小观测或收束。数值更接近 RTL 仍可能是偏差抵消；形成修复候选应有机制证据及与影响范围相称的验证。实验开关是否成为默认值由任务要求决定，不把某次对齐策略推广为全局惯例。

需要理解探针和归因的区别时，按需阅读 [Astar 案例](references/astar-lessons.md)。
